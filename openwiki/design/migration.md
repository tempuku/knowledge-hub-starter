# Migration and implementation sequence

Normative target; migration is NOT performed by this documentation change. Tracking: [issue #24](https://github.com/tempuku/knowledge-hub-starter/issues/24). Implementation must preserve all existing content, recorded evidence and histories. Do not infer dates, project membership or publication permission.

## M-01: Inventory before edits

Freeze one base commit and record its SHA. Produce a reviewed `migration/records-v1.json` machine-readable manifest in the implementation branch, schema_version=1, with base_revision and one item per non-index Markdown source, including directory log.md files. Each item has old_path, disposition, destination_path, allocated_record_id, source_sha256, legacy_log_path, legacy_event_ids, legacy_ui_ids, project_mapping, metadata_mapping, occurrence_source, and review_notes. Nullable fields are explicit. Disposition enum: `record`, `duplicate-change`, `summary-note`, `structural`. Store the human review report under `openwiki/design/` and link it from the index. No wildcard mappings or unreviewed defaults.

Every canonical concept becomes `record`; date-folder note with independent content becomes `record`, normally type note, filed by explicit topic mapping. A legacy journal page that only describes an update already represented in a native log becomes `duplicate-change` after exact identity/content evidence is reviewed. `log.md` summary with unique human content becomes `summary-note`, migrated as a normal note; an empty/redundant index summary becomes structural only with an explicit report entry. Never delete unique prose because a filename contains log.

The manifest supplies stable IDs once; reruns reuse them. It explicitly maps every legacy key: `project` slug to project record UUID; project records' legacy `project_id` slug to `x_legacy_project_id`; `type: journal` to note; missing status to draft only if review confirms unreviewed, otherwise require mapping; known status draft/stable/completed/deprecated preserved; unknown metadata retained under `x_legacy` without semantic reinterpretation. Existing `occurred_on` and supplied `occurred_at` retain their original factual value; invalid timestamps block migration until reviewed. Never infer local occurrence dates from Git.

Paths are selected by the reviewed manifest, not generated by an AI classifier. Root GUIDE/CI remain in place. Nested documentation follows its subject area. Duplicate titles are allowed, destination collisions are not. Empty date directories are removed only after all their contents have an accounted disposition and links have replacements.

## M-02: Preserve and transform histories

First archive original legacy log bytes and removed duplicate journal source bytes under `migration/legacy/`, with a manifest of exact hashes. This archive belongs in the same appropriately private source repository, is never a public deploy input, and is not parsed for current diary rows. The documentation-only PR does not introduce this archive.

Transform each existing native event into v1 wrapper, preserving full before/after source strings and original actor/summary, with new persistent event UUID mappings. Keep original timestamp in provenance.original_time; use it as recorded_at only when it is a valid known recording timestamp. Git-backfilled times remain labelled `git-backfill` and are not represented as actual occurrence times. Unknown recording time uses migration time with provenance.original_time=null and an Imported badge. If original times are decreasing relative to original event order, preserve sequence, use migration time for the entire affected chain, preserve all original times in provenance, and report the normalization explicitly. Do not reorder causally linked snapshots to fit dates.

Preserve legacy IDs in the migration manifest/alias map, not by rewriting original evidence. Use provenance kind legacy-log, legacy-journal or git-backfill. An existing record without a log gets an IMPORTED baseline with null before, exact old content as after, and migration timestamp; do not manufacture a CREATED date. If an existing native chain has missing revisions, mismatched snapshots or unexplained divergence from the current file, STOP and require documented repair from available evidence. Never fill gaps by inventing intermediate changes.

Append one IMPORTED normalization event per migrated record after preserved history: before equals previous after, after equals target canonical v1 content, path_after equals manifest destination, summary “Migrate record to hierarchical storage”, actor kind migration. This captures ID/frontmatter/link normalization and movement without rewriting old snapshots. The event is visible as Imported in Diary; ordinary views may filter action but must not hide migration by default. Logs now contain legacy snapshots plus a valid v1 head. Next native write must satisfy normal schema/chain rules.

For a duplicate legacy update journal, preserve unique summary/evidence in the archive and associate its old UI ID with the native event via explicit manifest mapping. If the journal carries unique substantive content, it must instead become a record. No deduplication by equal title, date, similar text or same Git commit alone. For independent journal notes whose creation is already in their sibling log, migrate the record/log once and do not project a second bare note row.

## M-03: Link and publication migration

Rewrite current relative record links to stable `record:<uuid>` links where appropriate; preserve structural index links. Resolve every current source reference. Populate old path and old UI ID aliases from reviewed mappings, including moved log path provenance. Historical bodies remain byte-identical, with resolution through aliases. GitHub source links remain external evidence, not internal identity.

Public policy is built from an explicit reviewed record-ID/event-ID allowlist. Preserve eligibility only where actual current visibility and snapshot eligibility satisfy P-04. Earlier inclusion in a buggy export is not authorization for a new exposure. No default “all imported events are public.” Reconcile expected public records, events, reminders, aliases and actor labels in a report. A public-to-private change is not claimed to erase prior public copies.

## M-04: Transaction and cutover

1. Build the migration in an isolated branch at the frozen base. No live writes during final cutover window; reject writes with a temporary Maintenance response before domain execution.
2. Validate a dry-run inventory: every original source has one disposition, every retained record has one log, all hashes/IDs/links resolve, all current canonical bytes equal final snapshots.
3. Run migration twice from the same base using the same manifest and fixed migration timestamp: resulting source trees and generated content must match exactly. Manifest also fixes event/operation/idempotency UUIDs; no new random IDs on rerun.
4. Build private/public candidate generations; compare expected event identities and counts, not just totals. New normalization events are listed separately; no unexplained loss/duplication. Test without .git to prove native history is sufficient.
5. Replace legacy writer imports and switch builder to native-only in the SAME implementation cutover. Reject new dated-journal records after cutover. Do not leave two writable models or auto-fallback to Git diffs. Existing compatibility readers operate only in migration tooling.
6. Publish one reviewed source commit via CAS against frozen base. If base changed, stop, refresh inventory and repeat dry run; do not silently merge new writes. Re-enable writes only after source and writer agree on schema.
7. Deploy complete candidate generation, check manifest and representative live routes, then mark migration complete. If build/deploy fails, keep prior live generation and show publication pending; source write success remains distinct.

Deployment rollback means switching the app to the last compatible generation, not restoring a past knowledge revision. Before any post-cutover writes, an explicitly authorized repository revert can undo the migration commit. After post-cutover writes, no automatic source rollback is allowed: fix forward to preserve new history. This does not add a user-facing Restore feature.

## M-05: Ordered implementation slices

| Order | Slice | Must be true before proceeding |
|---|---|---|
| 0 | Design baseline and issue acceptance | Exact merged design revision linked in #24; outstanding amendments explicit |
| 1 | Schema validator + shared writer + CLI/MCP adapter | W-01/W-02 acceptance passes against real temporary Git repos; no production migration |
| 2 | New projection builder and publication audit | Deterministic generations, policy filtering, no-Git rebuild, performance fixture pass |
| 3 | Shared routes + rendered record/history/diff + Diary | U-01–U-04 and accessibility/error tests pass on fixture data |
| 4 | Projects/Records/Search + Today/Calendar | U-05/U-06 complete with URL state, filters, offsets and mobile behavior |
| 5 | Reviewed inventory and migration dry run | M-01–M-03 reconcile every file and event |
| 6 | Atomic cutover and live verification | M-04 complete, no legacy writer, deployed manifest/routes verified |

Every slice starts with its issue checklist and produces a reviewable PR. Existing test assertions that assume date-folder storage must be replaced by target acceptance, not simply disabled. Keep current app usable until cutover. A blocked slice does not authorize inventing missing policy; update the design first.

This is concrete evidence that the old write paths do not enforce head equality. The unrelated demo is left unchanged and must be reconciled from evidence in the migration inventory.
